# Benchmarks

## Recall scorecard (4.0)

One command, reproducible from its seed, comparing the default recall path against
two baselines on the same turns:

```bash
bun run scorecard              # bun run scorecard --json --markdown for machines
```

**What the run is, stated so the table is not read as more than it is.**

- **Data**: 24 scenarios per family, generated by that command from seed `20261025`. It is *not*
  LongMemEval — that dataset is not vendored in this repository, and a run claiming it
  would be claiming something it did not do. Each scenario is eight turns holding one
  target fact and seven distractors, with one query per scenario.
- **Model**: none. With no provider configured the kernel runs `rule_only`, so the
  default path used no embedding model. The vector baseline embeds with a
  deterministic hashing vectorizer defined in `scripts/scorecard.ts`. The two are not
  "the same embedder", and this compares recall *paths* over text, not embedding
  quality.
- **Metrics**: `recall` is the target fact appearing in the returned context.
  `provenance` is a returned item carrying a stable identity and its ledger link — the
  baselines tie by construction, because a raw turn always carries its own id.
  `context tokens/turn` is `ceil(chars / 4)`, an estimate rather than a tokenizer
  count. `p95 latency` covers the recall call only, never ingestion.
- **Path**: all 24 items were served from `raw_evidence`; none was answered from
  compiled memory.

### Family A — one fact among distractors, queried with its own words

| arm | recall | provenance | context tokens/turn | p95 latency |
| --- | --- | --- | --- | --- |
| `cogmem_default` | 87.5% | 100% | 105 | 16.9 ms |
| `fixed_recent_window_4` | 45.8% | 100% | 70 | 0.0 ms |
| `vector_topk_3_hashing` | 100.0% | 100% | 53 | 0.2 ms |

### Family B — the same fact superseded, which is what the structure is for

The first family is lexical, so a vector ranker is expected to do well on it. The second
asks the question the structure exists to answer: a fact stated twice, the earlier statement
superseded, the query naming the thing rather than the value. `stale value leaked` is whether
the **superseded** value appears in the returned context at all — and it is measured twice,
once as written and once with the stale statement carrying the marker the host path honours.

| arm | current truth found | stale value leaked | provenance | context tokens/turn | p95 latency |
| --- | --- | --- | --- | --- | --- |
| `cogmem_default` | 75.0% | **95.8%** | 100% | 109 | 14.5 ms |
| `fixed_recent_window_4` | 87.5% | 0.0% | 100% | 74 | 0.0 ms |
| `vector_topk_3_hashing` | 100.0% | 100.0% | 100% | 59 | 0.2 ms |

### Family B′ — the same fact, with the stale statement marked

`status:superseded` is the marker the context planner honours when it decides what reaches
the model (`ContextCortex.hardSuppressionReason`). Nothing in `src/` writes it — it comes
from curation or review — so a run that marks nothing measures a system that was never
told, and the two cases are measured apart.

| arm | current truth found | stale value leaked | provenance | context tokens/turn | p95 latency |
| --- | --- | --- | --- | --- | --- |
| `cogmem_default` | 75.0% | 95.8% | 100% | 109 | 14.4 ms |
| `fixed_recent_window_4` | 87.5% | 0.0% | 100% | 74 | 0.0 ms |
| `vector_topk_3_hashing` | 100.0% | 100.0% | 100% | 59 | 0.1 ms |

### Family C — the host path, which is the one that matters

`kernel.recall` returns the *evidence list*; a host injects the *context plan*. They are
different artifacts, and they behave differently: the backend's recall items are mapped
into context candidates by `contextCandidateFromRecallItem`, which sets `superseded` from
the tag, and the cortex then decides what is selected.

| arm | current truth found | stale value leaked | provenance | context tokens/turn | p95 latency |
| --- | --- | --- | --- | --- | --- |
| `agent_backend_items` | 95.8% | 95.8% | 100% | 140 | 91.0 ms |
| `agent_backend_context_plan` | 95.8% | **0.0%** | 100% | 122 | 91.0 ms |

**The marked statement is excluded from the plan and kept in the evidence list.** That is
the designed behaviour, not a leak: the evidence list is evidence, with the tag visible on
the returned item for any caller that wants it, while the plan is what the model sees, and
there the superseded value is gone — for eighteen fewer tokens per turn.

**Two fixture flaws produced earlier readings of this, and both are worth stating** because
each looked like a product defect. In a run where nothing marks anything, the plan has
nothing to suppress, so Family B leaks for the honest reason that nothing knew. And two
families sharing project ids ingest the same turns twice, one marked and one not, after
which a recall can find the untagged twin and report leakage the marked neuron would have
been suppressed for. Each family now has its own projects.

### Where the default path loses

- **Recall, family A: 87.5% against the lexical baseline's 100%** — three misses of 24 — and
  it beats the recent-window baseline's 45.8%.
- **Context size**: 105 tokens per turn against 53 in family A, and 122 against 59 in family
  C. Roughly twice the context for less recall on lexical queries.
- **Latency**: 16.9 ms against 0.2 ms in family A. It does work the baselines do not.
- **Provenance: a three-way tie at 100%**, which carries little information, because every
  arm returns items that identify themselves.
- **Supersession**: with nothing marked, the default path carries the superseded value in 23
  of 24 scenarios, against 0% for the recent window and 100% for the vector ranker — and the
  window's 0% is not quality, since it cannot reach far enough back to see the stale turn.

**The `rule_only` qualifier applies to all of it**: with no provider configured, every
recall in these families was served from `raw_evidence`, so nothing here says what compiled
memory or the curation that marks a statement stale would do. It says what the paths do with
what they are given.

### The benchmark groups have no numbers to publish

**No suite is implemented.** `EvalRunner.runSuite` used to return a fixed table of
plausible values — 100% delivery, 0% leakage, a 0.05 token ratio — so `BenchmarkRunner`
compared constants against thresholds and the groups passed, and the proposal verdicts
that read those groups were decided by numbers that never depended on the proposal. That
is fixed: a suite reports `measured: false` and **no metrics**, a group whose suite
measured nothing has no baselines and cannot pass, and a proposal is not accepted on
unmeasured groups. The report says `not measured` in words rather than printing zeroes,
because a group that vanishes from a report reads like a group that passed.

`__tests__/eval-suites-unmeasured.unit.test.ts` holds that line: it fails if any suite
reports a metric, if any group passes without a measurement, and if the report stops
saying so. `BrainEval` is honest in a different way — it scores samples supplied to it —
and the scorecard above runs the kernel and measures it. The group machinery is the
placeholder, and it now says so instead of inventing numbers.
## BrainEval 3.6.0

`cogmem brain-eval --input samples.json` is the end-to-end memory-brain gate. It fails on recall below 90%, precision below 80%, provenance below 95%, binding purity below 90%, temporal current-truth accuracy below 95%, or any false entity merge, invalid user-belief ownership, context pollution, source mismatch, stale/cross-project leakage, context-budget violation, or prospective activation without confirmation. Input samples can include domain checks for canonical topic paths, entity merge decisions, user evidence ownership, temporal versions, context pollution, and exact source event identity.

Release fixtures must include at least one check for every domain metric. Missing binding, entity, user-belief, temporal, context-pollution, or source-fidelity checks fail closed instead of receiving a synthetic perfect score.

Episode fixtures also measure `episodeGroupingAccuracy`, `episodeBoundaryAccuracy`, `episodeEvidenceCoverage`, `unassignedRawRate`, `dreamCandidateGrounding`, `dreamBypassRate`, and `hermesImportParity`. These checks fail closed when omitted. Release gates require at least 95% episode evidence coverage, exact Hermes live/import shape parity, and zero governance bypass.

Atlas fixtures enforce project isolation, node/hop/evidence bounds, exact evidence locators, weighted path reconstruction, composable facet resurrection, pure read behavior, explicit activation touch, and canonical-source immutability. Runtime reliability fixtures cover read-only CLI inspection during a long-lived SQLite connection and audited `needs_confirmation` review transitions.

Strategy-policy evaluation consumes precomputed `StrategyRolloutOutcome` records:

```bash
cogmem brain-eval --input strategy-outcomes.json --strategy-rollout --json
```

It does not call a model or generate online rollouts. `StrategyDiversitySelector` can apply farthest-point selection to supplied vectors for offline fixture diversity. `ContextPolicyScorer` gates on median score, worst-decile score, exact source fidelity, zero unsafe/stale/cross-project leakage, zero over-budget outcomes, strategy adherence, and p95 latency. The top-fraction score is reported for exploration only and never overrides a safety failure.

Core benchmarks must prove natural memory emergence, not only recall@k.

## Natural Emergence Group

The `memory_natural_emergence` benchmark group runs on the `memory_recall` eval suite and tracks:

- `critical_memory_recall_rate`
- `old_but_important_recall_rate`
- `stale_memory_leakage_rate`
- `superseded_fact_leakage_rate`
- `suspect_memory_leakage_rate`
- `cross_project_leakage_rate`
- `provenance_completeness_rate`
- `context_budget_efficiency`
- `pulse_activation_useful_expansion_rate`
- `inhibition_correctness_rate`
- `vector_bytes_per_raw_event`
- `compiled_neuron_per_turn_rate`
- `immediate_embedding_skip_rate`
- `dream_coverage_rate`
- `undreamed_raw_backlog_count`
- `cold_recall_rehydration_success_rate`

This group checks both activation and inhibition: the kernel should surface old but important memories while suppressing stale, superseded, suspect, and cross-project evidence.

Storage metrics are quality gates, not standalone wins. A run only passes if vector bytes drop while critical recall, old-but-important recall, provenance completeness, and leakage metrics stay within the accepted threshold.

## Baselines

Use external benchmark ideas only as baselines or measurements:

- fixed recent window baseline
- vector topK baseline
- full-context baseline
- token saving metric
- latency metric
- provenance completeness metric
- immediate-compile-every-turn storage baseline
- selective-compile storage baseline
- raw-then-dream coverage baseline

These baselines must not become the default agent-facing memory path. The default path remains structure-first universe navigation with Pulse 1 and Pulse 2 activation, temporal traversal, governance suppression, and bounded context.
